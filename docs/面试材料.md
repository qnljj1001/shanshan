## 1. 3 分钟项目介绍

模板：

```text
我做了一个个人 / 企业文档知识库 AI 助手。

项目的背景是：普通大模型不能直接理解用户本地文档，而且回答容易没有依据。
所以我实现了一个支持文档上传、解析、向量检索和大模型回答的 RAG 系统。

用户可以上传 PDF、Word、Markdown、TXT 文档，然后通过聊天方式提问。
系统会先解析文档并切片，为每个 chunk 生成 Embedding，存入向量索引。
用户提问时，系统会检索最相关的文档片段，把这些片段作为上下文交给大模型生成回答，并在前端展示引用来源。

后续我还加入了文档总结、待办提取、周报生成等工具能力。
工程上使用 FastAPI、Vue3、SQLite、FAISS，并通过 Docker Compose 部署到阿里云。

这个项目的重点不是简单调用模型，而是完成了从文档处理、RAG 检索、回答生成、引用溯源、评估优化到部署上线的完整闭环。
```

## 3. 高频追问

### RAG 是什么？

RAG 是 Retrieval-Augmented Generation，检索增强生成。它先从外部知识库检索和问题相关的内容，再把检索结果作为上下文交给大模型生成回答。这样可以让回答基于用户自己的文档，并降低幻觉。

---

### 为什么需要 Embedding？

Embedding 把文本转成向量，让系统可以用相似度计算找到语义相关的文本片段。它解决的是“用户问法和文档原文不完全一样，但语义相关”的检索问题。

---

### chunk size 如何选择？

chunk 太小，上下文不足，模型可能缺少完整信息。chunk 太大，检索粒度粗，token 成本高，还可能引入无关内容。第一版使用 800 字左右和 120 overlap，再通过测试集对比优化。

---

### top_k 如何选择？

top_k 太小可能漏掉答案，top_k 太大会引入噪声并增加 token 成本。第一版默认 5，通过测试集比较 3、5、8 的效果。

---

### 如何减少幻觉？

主要方法：

1. 只允许模型基于检索片段回答。
2. 回答必须带引用来源。
3. 检索结果为空或低相关时拒答。
4. 建立无答案测试问题，检查模型是否编造。
5. 记录失败案例并调整 Prompt 和检索参数。

---

### 为什么第一版不用 Milvus？

第一版目标是先完成 RAG 闭环。FAISS 本地轻量，适合学习 Embedding 和向量检索。Milvus 更适合更大规模、更复杂部署场景，可以作为后续扩展。

---

### 为什么第一版不用 Redis？

当前第一版主要瓶颈是业务链路没有跑通。Redis 可用于缓存、限流或任务队列，但不是最小闭环必需。等系统稳定后再引入，能避免过早增加复杂度。

---

### Docker 解决了什么问题？

Docker 把应用运行环境、依赖和启动命令打包起来，保证本地和服务器环境一致。Docker Compose 用来编排多个服务，例如后端、前端、数据库、Nginx。

---

### SSE 和 WebSocket 的区别是什么？

SSE 是服务端到客户端的单向事件流，适合大模型流式输出。WebSocket 是双向通信，适合实时协作、聊天房间等场景。这个项目的模型流式回答用 SSE 就够了。

## 5. 项目亮点

面试时优先强调：

1. 不是只调用模型，而是做了完整 AI 应用闭环。
2. RAG 回答带引用，能减少无依据回答。
3. 有测试集和优化记录，不是凭感觉调参数。
4. 工程上有模块拆分、错误处理、日志、部署文档。
5. 项目能服务真实日常场景，如简历分析、JD 分析、学习资料问答。
