# RAG 设计

## 1. 目标

让模型回答基于用户上传的文档，而不是只依赖模型自身知识。

必须实现：

1. 能检索相关文档片段。
2. 回答中带引用来源。
3. 没有依据时拒答。
4. 可通过测试集持续优化。

---

## 2. 文档处理流程

```text
文件上传
  -> 文件类型识别
  -> 文本解析
  -> 文本清洗
  -> 文本切片
  -> 生成 Embedding
  -> 写入向量索引
  -> 保存 chunk 元数据
```

---

## 3. 文件解析策略

| 文件类型 | 工具 | 说明 |
| --- | --- | --- |
| PDF | PyMuPDF | 提取文本和页码 |
| Word | python-docx | 提取段落文本 |
| Markdown | 原生读取 | 保留标题结构 |
| TXT | 原生读取 | 按段落处理 |

解析后统一输出：

```json
{
  "document_id": "doc-id",
  "filename": "example.pdf",
  "pages": [
    {
      "page": 1,
      "text": "文本内容"
    }
  ]
}
```

---

## 4. 切片策略

第一版默认参数：

```text
chunk_size = 800
chunk_overlap = 120
```

切片原则：

- 优先按标题、段落、列表切分。
- 不要从句子中间硬切。
- 每个 chunk 保留来源信息。
- chunk 不要太短，否则上下文不足。
- chunk 不要太长，否则检索不准且 token 成本高。

chunk 元数据：

```json
{
  "document_id": "doc-id",
  "filename": "员工手册.pdf",
  "page": 3,
  "chunk_index": 12,
  "section_title": "报销流程"
}
```

---

## 5. 检索策略

第一版：

```text
embedding(question)
  -> FAISS similarity search
  -> top_k chunks
  -> prompt context
  -> LLM answer
```

默认参数：

```text
top_k = 5
```

后续优化：

- 对比 `top_k = 3 / 5 / 8`。
- 对比不同 chunk size。
- 加入 rerank。
- 加入关键词过滤。
- 加入文档范围过滤。

---

## 6. Prompt 策略

基础规则：

```text
你是一个严谨的文档问答助手。
你只能根据提供的文档片段回答问题。
如果文档片段中没有答案，请明确说“根据当前文档无法确定”。
回答时必须给出引用来源。
不要编造文档中没有的信息。
```

上下文格式：

```text
[来源 1]
文档：员工手册.pdf
页码：3
内容：...

[来源 2]
文档：员工手册.pdf
页码：4
内容：...
```

输出格式：

```json
{
  "answer": "回答内容",
  "sources": [
    {
      "filename": "员工手册.pdf",
      "page": 3,
      "reason": "该片段说明了报销流程"
    }
  ]
}
```

---

## 7. 拒答策略

以下情况应拒答：

- 检索结果为空。
- 检索分数低于阈值。
- 检索片段与问题明显无关。
- 模型回答无法对应到任何来源。

拒答示例：

```text
根据当前上传的文档，无法确定这个问题的答案。你可以上传更多相关资料，或换一种更具体的问法。
```

## 8. 面试可讲点

必须能解释：

- 为什么需要 RAG。
- Embedding 的作用。
- 向量检索如何工作。
- chunk size 和 overlap 如何影响效果。
- top_k 如何影响回答质量。
- 如何减少幻觉。
- 为什么回答要带引用。
- 如何评估 RAG 系统。
